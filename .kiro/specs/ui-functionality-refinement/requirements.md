# Requirements Document

## Introduction

This specification defines the requirements for refining the existing FastAPI + Vanilla JS data science platform by removing redundant functionality, consolidating profiling features, and implementing per-row data type management. The changes focus on improving user experience by eliminating confusion and providing more granular control over data transformations.

## Glossary

- **System**: The FastAPI + Vanilla JS data science platform
- **Automated_Profile_Section**: The redundant profiling section that exists separately from the Analyze section
- **YData_Profiling**: The ydata_profiling.ProfileReport feature for generating comprehensive data reports
- **Analyze_Section**: The main analysis section in the UI where profiling should be consolidated
- **Data_Section**: The UI section containing data management features
- **Change_Data_Type_Feature**: The per-row column type conversion functionality
- **Profile_Report**: The HTML report generated by ydata_profiling library
- **Browser_Tab**: A new browser window/tab opened via window.open()

## Requirements

### Requirement 1: Remove Redundant Automated Profile Section

**User Story:** As a user, I want a single, clear profiling feature, so that I'm not confused by duplicate functionality.

#### Acceptance Criteria

1. WHEN the system loads, THE System SHALL NOT display any "Automated Profile" section in the navigation
2. WHEN a user navigates through all sections, THE System SHALL NOT show any automated profile functionality outside the Analyze section
3. WHEN the backend receives requests, THE System SHALL NOT have any endpoints specifically for automated profiling separate from the main profiling feature
4. THE System SHALL remove all frontend navigation entries related to automated profiling
5. THE System SHALL remove all render logic and event handlers for automated profiling

### Requirement 2: Consolidate YData Profiling in Analyze Section

**User Story:** As a user, I want to generate comprehensive data profiles that open in new browser tabs like Jupyter, so that I can interact with the full report without leaving my main workflow.

#### Acceptance Criteria

1. WHEN a user clicks "Generate YData Profile" in the Analyze section, THE System SHALL generate a ProfileReport using ydata_profiling.ProfileReport with explorative=True
2. WHEN the profile generation completes, THE System SHALL save the report as an HTML file with a unique identifier
3. WHEN the HTML file is saved, THE System SHALL return the file via FileResponse with media_type="text/html"
4. WHEN the frontend receives the profile request, THE System SHALL open the report in a new browser tab using window.open()
5. WHEN the report opens in the browser, THE User SHALL be able to view the interactive HTML report
6. WHEN the user wants to save the report, THE User SHALL download it manually via browser controls (Ctrl+S / Save Page)
7. THE System SHALL NOT embed the report in an iframe within the application
8. THE System SHALL NOT convert the report to PDF format
9. THE System SHALL NOT return raw HTML as JSON response
10. THE System SHALL NOT force automatic download of the report file

### Requirement 3: Implement Per-Row Data Type Management

**User Story:** As a user, I want to change data types one column at a time with immediate feedback, so that I can handle conversion errors gracefully without affecting other operations.

#### Acceptance Criteria

1. WHEN a user views the Data section, THE System SHALL display a table with columns for Column Name, Current Data Type, Target Data Type, and Action
2. WHEN the table loads, THE System SHALL show Column Name as static text for each column
3. WHEN the table loads, THE System SHALL show Current Data Type as read-only text for each column
4. WHEN the table loads, THE System SHALL show Target Data Type as a dropdown with the current type selected by default
5. WHEN the table loads, THE System SHALL show a Save button for each row that is disabled by default
6. WHEN a user changes the target data type dropdown, THE System SHALL enable the Save button only if the target type differs from the current type
7. WHEN the Save button is enabled, THE System SHALL display it in blue color
8. WHEN a user clicks Save for a row, THE System SHALL send one API request for that single column conversion
9. WHEN a conversion succeeds, THE System SHALL update the Current Data Type text immediately in the UI for that row
10. WHEN a conversion fails, THE System SHALL display an inline error message for that specific row only
11. WHEN a conversion fails, THE System SHALL NOT block other rows from being processed
12. WHEN a conversion fails, THE System SHALL NOT throw global alerts or errors
13. WHEN the backend receives invalid conversion requests, THE System SHALL reject the conversion with a clear error message
14. WHEN the backend processes conversions, THE System SHALL NOT partially mutate the dataset on failure
15. THE System SHALL process exactly one column conversion per API request
16. THE System SHALL NOT support batch conversions of multiple columns
17. THE System SHALL NOT allow silent failures in data type conversions

## Special Requirements Guidance

### Parser and Serializer Requirements

This feature does not involve parsing external data formats or serialization beyond standard JSON API communication, so no special parser/serializer requirements apply.

### Error Handling Requirements

- All data type conversion errors must be scoped to individual rows
- Backend validation must prevent invalid conversions before attempting them
- UI must provide immediate feedback for both success and failure cases
- No global error states should be triggered by individual conversion failures
